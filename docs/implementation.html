节奏康复：技术实现路径 v1.0

从手机摄像头到云端记录，拆解实现路线、协作接口和三人交付安排。

技术方案 v1.0
下载原文 ↓

日期：2026-09-11｜交付目标：2026-09-13 下午｜团队：3 人，主要使用 AI 辅助开发

状态：基于官方文档核查的工程建议及实施任务，不是已运行或已通过真机测试的实现。对应需求：PRD v2.0。本次工作产出文档，没有创建云服务、部署产品、生成三个主题或训练识别模型。

1. 推荐路线与优先验证#

采用一个 React + TypeScript + Vite 手机网页项目，同时承载用户页面和治疗师页面。浏览器内使用 MediaPipe Hand Landmarker 提取手部关键点，自定义三手型识别与时间规则；预先生成并剪辑音乐、动画，合成一个带音轨的 MP4；Supabase 提供匿名身份、治疗师账号和数据库，Cloudflare Pages 作为首选静态托管候选。

这是为了尽量减少两天内需要维护的系统数量。素材生成在开发阶段完成，正式训练不调用多模态 LLM；“识别负责人”的首要工作是使用预训练关键点模型并验证分类规则，不默认从头训练视觉大模型。

官方支持能力：Hand Landmarker 可在 Web 输出 21 个手部关键点；推理调用同步阻塞，官方建议使用 Worker 避免阻塞界面。其输出的左右手类别分数不能当成自定义动作置信度。MediaPipe Web 文档

现成 Gesture Recognizer 的默认分类包含张掌和握拳，但没有钩拳。因此不能只读取默认标签就声称完成三动作识别。默认手势列表

前 3 小时先完成两个可行性检查：①iPhone 和安卓上的 STRAIGHT/HOOK/FIST 区分；②实际手机网络访问部署页、模型、视频和云端写读。任一失败即记录问题，不先堆完整 UI。当前工作环境没有接入两类手机，故这里没有真机结果。

3. 手部识别：先关键点，再规则#

3.1 摄像头与准备#

HTTPS 页面中请求 getUserMedia，audio:false，facingMode:user，分辨率 ideal 640×480、帧率 ideal 30；允许浏览器返回不同参数。摄像头预览 muted、playsInline，视觉上镜像；分类使用原始帧坐标，镜像只用于显示。仅录入单手，不保存视频。

getUserMedia 要求安全上下文和用户授权，拒绝权限必须处理；localhost 的本地开发可用并不证明手机通过局域网 HTTP 能用。MDN 摄像头文档

训练前选择左右手并依次练习三姿态，每类稳定保持约 2 秒，采集仅在本机内存里的关键点作为校准参考。手型不能区分则提示转动少量角度、增加光线或调整取景，最多两轮重试，再显示无法完成当前环境校准。校准和教学不进入训练统计。

不能把用户随意摆出的三种姿势仅按时间标签学习成正确姿势。校准样本必须先通过宽松的解剖结构规则，再用于调整个体阈值；错误示范不能被“校准”洗成达标。

3.2 特征和分类#

使用 21 个关键点估计手指 MCP/PIP/DIP 弯曲形态，辅以指尖到掌心距离并以掌宽归一化。用估计的 world landmarks 构造特征，但不把其米制数值或计算角度称为医学测量。左右手统一成同一局部坐标约定。

建议分类逻辑：STRAIGHT 为四指各关节整体伸展；HOOK 为 MCP 相对伸展且 PIP/DIP 弯曲；FIST 为 MCP 与指间关节同时弯曲。使用多指一致性和分类间隔防止单指遮挡造成误判；过渡态返回 UNKNOWN，不强行挑最近类别。

第一版先用明确关节规则 + 本人校准模板。各阈值集中配置，通过人员独立的短测试集调节，不在文档中编造经过验证的角度界限。若 HOOK/FIST 分不开，先验证关键点是否可信，再考虑小分类器；关键点本身失真时，叠加分类器无法自动解决。

跟踪质量与动作分类必须分开：有完整、合理关键点但动作错误返回 tracked+UNKNOWN，继续计分；无手、关键点异常、取景裁切或样本过期返回 untracked，按丢失逻辑暂停。左右手分数不是动作质量分，模型结果也不保证提供每点 visibility，不依赖不存在的字段。

建议防抖默认：同类持续 200 ms 后发布稳定姿态，保留该稳定序列首帧的时间作为到达时刻；过渡手型立即停止累计保持。输入间隔超过 150 ms 不计跨帧空白保持时间；连续 500 ms 无可靠跟踪则暂停。参数版本写入结果，真机调试后冻结。

只用手部关键点不足以可靠测量手腕相对前臂的屈伸角。首版通过示范和取景引导提醒手腕保持直，不开发或宣传“实时医学级腕角度安全拦截”。

3.3 推理线程和性能#

优先 Worker 内执行 VIDEO 模式推理，以采集时的 performance.now() 单调时间戳调用 detectForVideo。每次最多一个在途帧，丢弃积压帧；目标先取 15 Hz，不按视频 30 帧全部推理。

发送 ImageBitmap 时随帧附上采集时的媒体时间、会话 epoch 和任务号；返回后释放图像资源。暂停、重播、切歌时递增 epoch，丢弃旧 epoch 结果。不能用推理结果到达主线程的时间判节奏，否则模型延迟会变成用户迟到。

Worker/图像传输或后端在某测试浏览器不可用时，降级主线程限频 10 Hz、低分辨率；若仍持续卡顿，明确该环境不能开始，不能绕过摄像头要求。GPU 可用性需要实测，不预设所有 Safari 支持同一种 Worker/GPU 组合。

4. 动作谱面、时间轴与评分#

4.1 统一的内容合同#

三个主题共用 protocolId=tendon-a-demo-v1。建议默认 60 BPM，每手型 6 拍，三手型循环 5 次。正式媒体长 90 秒，倒数和教学单独展示。每 6 秒任务的前 2 秒提供动作预告，到第 2 秒出现目标节拍，剩余时间可保持姿态。

以下为首版合同示意，实施时生成 15 个 task，startMs=6000×i、targetMs=startMs+2000、endMs=startMs+6000：

type Pose = 'STRAIGHT' | 'HOOK' | 'FIST' | 'UNKNOWN';
type Grade = 'PERFECT' | 'GOOD' | 'MISS';
interface Task {
  id: string;
  pose: Exclude<Pose, 'UNKNOWN'>;
  startMs: number;
  targetMs: number;
  endMs: number;
  holdMs: number; // 3000，来源于所选动作示例，不是临床自动处方
}
interface ThemeManifest {
  id: string;
  title: string;
  protocolId: string;
  version: string;
  bpm: number; // 首版 60
  videoUrl: string;
  posterUrl: string;
  durationMs: number; // 首版 90000
  tasks: Task[];
}
interface PoseSample {
  epoch: number;
  capturedPerfMs: number;
  capturedMediaMs: number;
  tracked: boolean;
  pose: Pose;
}

这套合同是内容与软件协作的关键：A 按时间表制作，B 按时间表评分，C 按时间表显示示范。若改变 BPM、任务数量或保持时间，应同步发布新 protocolId/manifest 版本，不能只换视频长度。

4.2 播放主时钟#

音乐与画面离线合成为同一 MP4，只使用一个有声媒体元素播放。video.currentTime 为判定主时钟；requestAnimationFrame 更新 UI，不用 setInterval 累加游戏时间，不用另一条独立音轨计时。摄像头预览是另一 muted 视频，与内容媒体分开。

用户点击“开始”后调用 play() 并处理 Promise 失败；设置 playsInline，避免 iPhone 自动全屏遮掉评分层。模型和当前媒体准备完成后才允许开始。移动端有声自动播放存在限制，不能依赖页面加载后直接响起。MDN 自动播放、MDN video

不显示原生可拖动进度控件，playbackRate 固定 1；监听意外 seek 与播放中断并暂停。媒体 waiting/stalled、页面隐藏、用户暂停时停止计分和有效时长累计。前台恢复不能把后台经过的时间补算为训练。

4.3 两个独立结果#

对每个任务记录“首个稳定到达目标手型的时间”，只评一次节奏，不能反复试到 Perfect。稳定判定使用序列首帧时间；若任务开始前就保持该手型，则到达时刻按任务开始记为提前到达，不在目标拍到来时再次虚构动作。

  • |到达时刻−目标时刻|≤300 ms：Perfect。
  • 大于 300 ms 且≤750 ms：Good。
  • 其余时刻或从未达到：Miss。
  • 独立检查任务区间内是否有连续 3000 ms 有效目标姿态，达到则动作完成；姿态中断需重新保持，不能把零散时段拼成连续 3 秒。

例：第一个任务区间 [0,6000] ms，目标 2000 ms。用户在 2900 ms 达到姿势并保持到 5900 ms，则节奏 Miss、动作完成。用户在 2100 ms 达到但 2500 ms 松开，则节奏 Perfect、动作未完成。视频均继续按原时间播放。

UI 可即时显示已发生的节奏结果和保持进度，但任务到区间末尾才确认结果。若跟踪故障可能跨越结算边界，最多等待 500 ms 质量确认期；确认是跟踪中断就进入暂停并回滚受影响的最早未确认任务，不把它结为 Miss。

最终成绩：动作完成率=动作完成任务数/15；节奏成绩=100×(Perfect+0.6×Good)/已结算节奏任务数，四舍五入至整数。未到达和因故暂停重播的未确认任务不增加 Miss。中途退出的当前任务若已经产生有效节奏到达，可保留其节奏结果；否则不强行追加该任务的 Miss；保存任何已满足保持的动作结果，但标记会话未完成。

首版不做设备自动音频延迟补偿。使用手机扬声器验收，蓝牙音频不同延迟可能影响踩拍结果；将设备与音频路径记录在测试表，不把示例窗口宣传为所有设备的公平精密测量。

4.4 会话状态#

状态：PREPARING → TUTORIAL → READY → COUNTDOWN → PLAYING ↔ PAUSED → COMPLETED / ABORTED。

暂停恢复建议：记录最早受影响未确认任务，稳定入镜 1 秒后倒数 3 秒，回到该任务 startMs 重播，重置该任务临时到达/保持记录；已确认任务不动。倒数期间若再次丢手则回到 PAUSED。缓冲后恢复需用户点击继续以满足移动端播放限制；单纯丢手可尝试自动倒数恢复，play() 被拒绝再显示继续按钮。

每个任务确认后写 IndexedDB，播放时每秒保存一次会话检查点，转换状态立即写入。刷新后将未结束会话整理为 ABORTED；不依赖 beforeunload 成功上传。有效时长累计真实前台播放区间，暂停重播时间算练习时间，但不得把重播变成双倍任务数。

到媒体 ended、各任务完成结算且播放路径未非法跳转后才产出 COMPLETED。等候最后一帧推理及质量确认不超过 500 ms；如果末尾存在跟踪故障则进入恢复流程，不先发打卡。

5. 音乐与视频素材任务#

建议萌宠、花园、星空三个主题，制作要求相同：60 BPM、90 秒正式段、15 个动作任务。每任务第 2 秒安排明显但温和的节拍提示。实际节拍由剪辑/音频工程对齐，不能仅凭生成提示词写了“60 BPM”便认定成品节拍正确。

素材 A 的交付包：每主题一个 poster.jpg、一个带音乐的 training.mp4、一个 manifest.json 和来源说明。母版可保留无音视频与音频，供重剪；网页仅播放合成成品。

建议编码：竖屏 540×960、H.264、yuv420p、30 fps、AAC 音轨、faststart；每主题文件目标≤15 MB，模型和每个媒体文件都需检查托管大小限制。优先只准备当前主题，不在首页同时下载三段视频。

用短片段生成、剪辑拼接为连续 90 秒。画面底部预留动作示范与保持进度区域，顶部预留评分和暂停区，避免关键角色被覆盖；可以为页面预留区域但不要把固定坐标画进生成提示作为唯一约束。动画不生成 Perfect/Good/Miss、计时器和中文动作说明，由网页渲染真实状态。

动作示范与情境动画分开制作：三个正确手型的图/真人片由 B 与 A 对照原资料检查，尤其钩拳和握拳；生成画面若出现畸形手、错误关节、错字或暗示用力动作需替换。保留音乐、视频生成服务及素材来源的使用权说明。

先交付一个可播放主题供集成，再完成其余两个。三主题是交付目标，不能用三张封面指向相同素材冒充完成。

6. 身份、绑定、数据和访问控制#

6.1 身份路线#

未绑定时允许纯本机训练，用 localProfileId 区分当前浏览器档案。点击绑定时在线调用 Supabase signInAnonymously() 获取服务端匿名用户 ID，并将此本机档案与其固定关联；已有有效会话则复用。创建失败时保留本机体验，但不伪装绑定成功。

匿名身份在该浏览器持久化；清除数据或换设备不可恢复是已接受限制。患者与治疗师入口分别使用不同 Auth storageKey，避免同一浏览器登录治疗师覆盖患者身份。切换到未知患者云身份时，不自动把现有本机队列上传给新身份。

Supabase 支持不填写邮箱的匿名身份；匿名用户依然属于 authenticated 数据库角色，不能把 publishable/anon key 当成患者身份。匿名身份文档

6.2 最小数据表#

表 核心字段与约束
profiles id=auth user id、display_name、role=user/therapist；role 仅由受信服务端设置
therapist_invites therapist_id、随机 8 位大写字母数字码的服务端摘要、enabled；不允许浏览器直接列出全表
bindings user_id 唯一、therapist_id、bound_at、consent_version；一用户最多一当前绑定
training_sessions id=客户端 UUID、user_id、theme_id、protocol_id、manifest_version、rule_version、started_at、ended_at、status、active_duration_ms、planned_duration_ms、total_tasks、completed_tasks、perfect/good/miss、judged_tasks、received_at

训练详情每任务记录先留本机，云端首版上传会话汇总已满足治疗师查看需求。总数、范围及比例由服务端校验，展示比例从计数计算。不能信任前端上传的 therapist_id 或“我有治疗师权限”。

打卡由 status=completed 的训练记录推导，不单建可重复计数的打卡表。同日多次通过 completed 的 ended_at 转 Asia/Shanghai 去重；服务端另记 received_at 区分训练时间和补传时间。客户端时间异常标记，不以此进行医疗判断或竞赛排行。

浏览器上报的评分无法等同于防作弊认证或临床测量，首版用于训练记录展示。服务端验证格式和访问权限，不伪称服务端已经重算原始视频。

6.3 服务接口#

接口 输入/输出与行为

listMySessions 当前用户 → 自己的记录
listBoundUsers 治疗师令牌 → 当前已绑定用户
listUserSessions 治疗师令牌、目标 user_id → 校验当前绑定后返回记录

这些接口可由 Supabase 数据 API + RLS、数据库事务函数和少量 Edge Function 实现，不需要再搭完整 Express 服务。邀请码解析/确认由服务端封装，绑定事务复核 code enabled 与 therapist role；客户端不能直接写任意 bindings。

建议邀请查询按用户每分钟最多 5 次，必要时结合 IP 限流；随机码不包含姓名手机号。初始治疗师账号在服务后台预置，客户端不能自注册成治疗师。匿名注册开启服务端防滥用措施，先验证同一现场网络下的并发注册；默认 IP 限流可能影响多人同时扫码，不能不测试就无限放开。

权限测试不可省：用户仅写自己的会话，治疗师只读当前绑定用户，解除后不可读；profiles 的角色字段无客户端修改权限，invite 全表不公开。Supabase RLS 和表授权都需配置，所有暴露表启用 RLS；service_role/secret key 仅服务端持有。RLS 官方说明

6.4 本机优先与补传#

结束时先把结果与 sync_state 写入 IndexedDB，界面立即显示本机打卡结果。有已绑定云身份时再上传；成功后标记 synced，失败保持 pending，并显示“已保存在本机，待同步”。

排队任务始终带固定 ownerAuthId 和 session UUID。网络恢复、重新打开页面、点击重试时补传，建议失败后 2/5/15/30 秒退避，离线时停止轮询。同 UUID 重传只能形成一条同用户记录；提交数据变化或他人 UUID 冲突应报错，不能覆盖其他记录。

绑定确认后上传用户同意共享的历史；解除绑定后暂停共享上传但保留本机记录。重绑时再确认整个当前档案的分享范围。治疗师只看已经成功上传的数据；页面显示刷新时间，不制造“即时同步成功”。

7. 部署、移动端与网络#

优先部署 Vite dist 到 Cloudflare Pages，项目输出与构建命令按 Vite 工程配置；包含 SPA 路由回退，刷新治疗师详情页也可打开。模型、WASM 和主题文件使用同源固定路径，避免训练现场临时依赖第三方模型 CDN。Pages 的 Vite 部署说明

此托管候选与 Supabase 尚未在现场网络测试，不保证中国大陆各网络表现。先用一条真实 HTTPS 地址验证 iPhone、安卓、会场 Wi-Fi 或同类 Wi-Fi、手机蜂窝网络上的资源加载及云端绑定写读。海外服务不可达时是明确交付风险，不可用模型在开发机可下载替代现场测试。

若选定服务不通过，优先切换团队已有、手机实测可达的 HTTPS 托管与后端，维持本方案接口；当前未发现可用账号或已部署服务，因此不虚构已就绪的国内备选。不要临近交付同时重写整个后端。云端未能解决则治疗师闭环不算验收通过，必须明示，不能展示假同步。

基线浏览器：可测试的 iPhone Safari 与安卓 Chrome/系统浏览器；记录版本并发布支持说明。微信内置浏览器尽力支持，失败展示“复制链接并在系统浏览器打开”；不同浏览器存储不共享，首次进入微信时尽早完成能力检测与跳转提示，避免在微信建档后才要求换浏览器。

绑定/云登录网络故障不阻止已有本机训练；相机或模型失效则不能进入计分训练。视频完整缓存/可连续读取是减少中途缓冲的优先项，缓存策略须真机验证；不承诺首次访问可离线。

8. 三人执行顺序#

时间按 9 月 11 日开始安排；若实际开工更晚，优先保留识别验证、第一主题闭环和双平台验收，压缩装饰性内容。

9. 验收用例与阻断标准#

以下数值为内部演示质量目标，均未测量，不能放进宣传材料声称已达到。

9.1 识别与体验#

  • 三名成员在 iPhone 和安卓各完成每姿态 10 次，合计 180 次；记录三分类混淆表、错误接受与丢失。用于初始工程检查，不构成临床准确率研究。
  • 每姿态有效识别≥90%作为继续集成目标；HOOK/FIST 混淆≤10%。调参后保留未参与调参的人员/片段复测，不能只报告训练样本结果。
  • 错误手型、转场、空画面不能持续产生达标；同一个静止手型不能让全部 15 任务完成。
  • 目标推理频率≥10 Hz；画面卡顿或故障暂停过多即不通过，即使总体分类比例达标。
  • 三主题逐一核对共 15 任务、时长 90 秒、节拍提示与 manifest 一致；建议导出对齐偏差≤100 ms。

9.2 可自动验证的核心逻辑#

对纯评分函数使用 Vitest 注入时间事件，不依赖摄像头：±300/±750 ms 边界；2999/3000 ms 保持；迟到但动作成功；准点但保持失败；跨任务不能复用保持；静止提前姿势不能反复计节拍。

测试丢手跨结算点不增加 Miss、暂停重播不重复得分、旧 epoch 推理被丢弃、末尾丢手不能提前打卡、退出不打卡、刷新恢复未完成、背景时间不计训练、未进入任务不加 Miss、分母为零显示空值。

9.3 数据与权限#

  • 两个匿名用户、两个治疗师实际建立交叉绑定；直接发请求验证用户互不可读写、治疗师越权返回拒绝/空结果。
  • 昵称更改不能提升 role；更换请求中的 user_id/therapist_id 不能绕过授权；解除绑定后重新请求立即失权。
  • 同一记录上传三次仍只有一条；离线完成后联网补传成功；更换匿名身份后不上传旧身份队列。
  • 正常网络下上传后 15 秒内治疗师刷新可见作为测试目标；等待失败时两端状态诚实一致。
  • 多人共用 Wi-Fi 测匿名注册限流，治疗师与患者会话互不覆盖。

9.4 发布前检查#

两平台各测摄像头拒绝、权限恢复、音频启动失败、切后台、锁屏、视频缓冲、网络断开和手移出画面。用真实二维码从微信进入，再检查系统浏览器回退路径。

检查前端产物无服务器密钥，无真实患者原始视频，无可公开列举的绑定数据，无正式环境模拟成绩。准备两台已验证演示手机及备用网络，但观众扫码链路仍需实测。

若首日关键点无法区分 HOOK/FIST：先调整取景与阈值并复测；仍不通过，向产品负责人提交具体混淆结果与可行选项。更换动作组需要同步调整文献说明、时长和三主题合同，不得静默把钩拳视为握拳。未能满足关键能力时如实标记未完成。

10. 交接给三位成员的简短任务书#

A（素材）：按 60 BPM、90 秒、15 个六秒任务制作三套不同视听主题；每个任务第 2 秒为目标拍。先给一个完整主题，随后补两个。提供 MP4、封面、manifest、素材来源与动作示范，视频内不烘焙成绩文字。

B（识别与核心）：先证明两个平台能区分三手型，并测云服务连通；再按本文合同输出 PoseSample，实现时间轴、动作保持、节奏评分、暂停恢复、本机队列与权限受控的绑定上传。首版默认复用模型，不从训练模型开始。

C（前端）：完成扫码首页、主题选择、教学取景、训练叠加层、结果历史、邀请码确认和治疗师后台。通过固定接口接 B 的模块，不在组件内部另算一套成绩；开发模拟事件在正式构建禁用。

最终交付应同时附上：可访问网址与二维码、部署版本/依赖锁文件、三套资源与 manifest、治疗师测试账号的私下交接、真机机型版本和验收结果、已知限制。本文中的账号、可达性、识别性能尚未验证，不以文档代替测试证据。
